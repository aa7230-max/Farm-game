# 성능 설계 보강 (설계서 v0.2 부록)

> 근거: 구름이 워커 노트에서 나온 제안(로컬 모델이 작성, 검증 전 아이디어)과 설계서 v0.1 7-3 성능 가이드.
> 아래 항목은 **M0에서 실제로 측정해 효과를 확인한 뒤** 채택합니다. 측정 전에는 "권장안"으로만 봅니다.

## 1. 오브젝트 풀링
- 몬스터, 이펙트, 꽃잎·반딧불 파티클은 시작할 때 미리 만들어 두고 재사용합니다.
- 프레임마다 생성·파괴를 반복하지 않습니다. 가비지 컬렉션(GC) 스파이크의 주된 원인이 됩니다.
- 풀 크기는 최대 동시 개수 기준으로 잡습니다. (예: 웨이브당 최대 몬스터 수 + 여유분)

## 2. 링 버퍼로 위치 샘플 보관
- 4인의 위치 데이터(10Hz)는 고정 크기 링 버퍼에 저장하고 보간에 씁니다.
- 배열을 새로 만들거나 늘리지 않으므로 메모리 재할당이 없습니다.
- 플레이어마다 버퍼 하나씩, 최대 4개만 유지합니다.

## 3. 고정 크기 블록 풀 (자원 관리)
- 지오메트리와 텍스처는 용도별로 고정 크기 블록에서 할당합니다.
- 장시간 플레이 시 메모리 파편화를 줄여 모바일 메모리 부족을 늦춥니다.
- 방 입장과 퇴장, 테마 전환 때 자원을 해제하고 다시 채우는 흐름을 정해 둡니다.

## 4. 프레임당 할당 금지
- 렌더 루프에서 `new Vector3()`, `new Color()` 같은 객체 생성을 하지 않습니다. 임시 객체를 미리 만들어 재사용합니다.
- JSON 파싱과 테마 데이터 로딩은 게임 시작이나 방 입장 시점에만 합니다.
- 이벤트 핸들러에서 문자열을 계속 만드는 코드도 피합니다.

## 5. 렌더링 기법
- 풀숲, 나무, 꽃은 `InstancedMesh`로 묶습니다 (v0.1 7-3과 동일).
- 텍스처는 아틀라스 한 장으로 합치고 밉맵을 씁니다.
- 모델은 GLB, 텍스처는 WebP 또는 KTX2로 압축합니다. 파일당 수 MB 이내를 목표로 합니다.

## 6. 측정 계획 (M0)
| 항목 | 측정 방법 | 목표 |
|---|---|---|
| 프레임 시간 | 브라우저 개발자 도구 Performance 탭 | 60fps 기준, 중급 안드로이드 30fps 이상 |
| GC 빈도 | 개발자 도구 메모리 탭 | 플레이 중 주기적 대형 GC 없음 |
| Draw call | Three.js `renderer.info` | 150 이하 |
| JS 힙 | 메모리 스냅샷 | 4인 플레이 1시간 후에도 우상향하지 않음 |
| 기기 | 아이폰 Safari(Xcode 시뮬레이터 + 실기기), 안드로이드 Chrome(실기기) | 두 플랫폼 모두 측정 |

## 7. 맥미니에서 할 수 있는 것
- 맥미니 Safari와 Xcode iOS 시뮬레이터로 아이폰 Safari 동작을 먼저 확인합니다.
- 실기기 측정은 아이폰과 안드로이드 기기가 필요합니다.
